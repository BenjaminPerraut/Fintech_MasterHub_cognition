# Decisions

Short, dated decision records. When a choice was made under the 2-hour budget, the
trade-off is written down here instead of being discussed live.

| ID | Decision | Why | Trade-off / what prod would do |
|----|----------|-----|--------------------------------|
| D-001 | **FastAPI + Jinja2 server-rendered HTML + SQLite**, no SPA, no ORM | No Node on the box; fewest moving parts to audit; every SQL write is visible in `app/` | No offline/realtime UI. Prod: Postgres (same SQL, swap `db.py`), keep server rendering or add HTMX |
| D-002 | **Stub IdP behind `IdentityProvider`** (`app/auth/provider.py`) | Real Entra/Okta needs tenant + secrets we don't have | Stub accepts any seeded subject without a password. Must never be enabled outside sandbox. See `docs/SSO.md` |
| D-003 | **Roles come from IdP group claims, one role per person** | Matches how Entra/Okta groups work; holding two roles is how people approve their own work | A user who legitimately needs two hats needs two accounts. Login with conflicting groups is refused and audited (`max.dual` demo account) |
| D-004 | **Hash-chained audit log + SQLite triggers blocking UPDATE/DELETE** | Triggers were trivial in SQLite (2 statements). `/audit/verify` recomputes the chain | Tamper-*evident*, not tamper-proof: someone with raw file access can drop triggers and rebuild the whole chain. Prod: Postgres with `REVOKE UPDATE, DELETE` from the app role + periodically anchor the head hash to WORM storage (S3 Object Lock) or a ledger |
| D-005 | **Business change and its audit event are written in the same transaction** (`BEGIN IMMEDIATE`) | No change without an event, no event without the change; immediate locks keep the chain linear | Single-writer throughput (fine for an internal tool; ~thousands of writes/s on SQLite) |
| D-006 | **Admin is not a superuser** | Fintech control: IT admins manage people, they don't approve KYC or money movement | Admin must ask an Ops Lead for business actions, by design |
| D-007 | **DB row is the source of truth on every request** | Deactivating a user or changing a role takes effect on the next click, not at session expiry | One extra indexed query per request |
| D-008 | **Global CSRF dependency** on the FastAPI app, strict CSP (no inline JS/CSS), `no-store` caching, no `/docs` or `/openapi.json` | Can't forget CSRF on a new route; PII pages must not be cached; less attack surface | JS must live in `/static`. No public API in this POC (would use OAuth2 client credentials + scopes) |
| D-009 | **Session: signed cookie (itsdangerous), HttpOnly, SameSite=Lax, 8h absolute expiry**, ephemeral key if `MASTERHUB_SECRET_KEY` unset | No server-side session store needed | Can't revoke one session server-side except via user deactivation (D-007 covers the important case) |
| D-010 | **Access denials are audited** (`access.denied`) | Probing for permissions is a signal a fintech wants to see | Audit log grows with noise from misclicks; acceptable |
| D-011 | **One generic `items` table (JSON `data`) for every queue app**, schema defined by the YAML manifest | Adding app #11 = one YAML file, no migration | Filtering uses `json_extract` (no typed indexes). Prod: Postgres JSONB + expression indexes, or typed tables generated from manifests |
| D-012 | **Four-eyes = propose then approve.** A `four_eyes` transition only creates a `decisions` row; a *different person* with an `approve_roles` role applies it | Simple, explicit, auditable; same flow for KYC, refunds, rollouts | Enforced 3 times: service check (`approve()`), DB trigger `decisions_four_eyes`, and tests. Compared by person (`subject`), not role, so a promotion doesn't let you approve your own proposal |
| D-013 | **Records carry a content hash; every change audits `before_hash`/`after_hash`** | Answers "did anyone change the record afterwards?": `/audit/verify` flags rows edited outside the engine, even if the attacker recomputes the row hash | Detects, doesn't prevent. Item tables still accept direct SQL from someone with DB access |
| D-014 | **Optimistic locking via `version`** on every action form | Two analysts acting on a stale screen get a 409 instead of silently overwriting | User has to reload; acceptable |
| D-015 | **PII masked by default; reveal is an explicit, audited POST** (`pii.revealed`); CSV exports are always masked and audited (`data.exported`), with a CSV formula-injection guard | Least privilege + evidence of who looked at what | No field-level encryption at rest (D-016) |
| D-016 | **No encryption at rest / field-level encryption** | Time budget | Prod: encrypted volume + KMS envelope encryption for PII columns |
| D-017 | **Retention: `retention_until` = relationship end + 5 years, filterable, with "purge due" quick filter.** No automatic purge | Deleting regulated data needs legal-hold checks and a four-eyes purge job; not something to rush | Prod: scheduled purge job → four-eyes approval → hard-delete PII, keep a tombstone + audit event |
| D-018 | **Items cannot be deleted** (trigger); comments and closed decisions are append-only | Mistakes are corrected by a new action, never by erasing history | Purge (D-017) will need an explicit, audited exception path |
| D-019 | **Engineers cannot view KYC**; Support sees it masked and read-only; Admin has no access | Need-to-know for customer PII | Engineers debugging prod issues need a break-glass flow (not built) |
| D-020 | **Conditional four-eyes (`four_eyes_if: {field: amount, gte: 500}`)** instead of a separate "large refund" state machine | One manifest line expresses the policy; threshold is visible to auditors in YAML and stamped on every proposal (`four_eyes_rule`) | Single numeric threshold per transition. Unparseable amounts fail closed (treated as needing four-eyes) |
| D-021 | **Votes are final, one per person, creator can't vote, down votes need a reason** (`votes` table: UNIQUE + no-UPDATE/DELETE triggers) | No vote-flipping, no self-voting, every objection is explained | Changing your mind means commenting, not re-voting. Votes from an earlier round stay counted if a flag returns to voting (not reachable in the current manifest) |
| D-022 | **Quorum = N up votes AND more up than down** (`requires_quorum` on the transition) | Simple, explainable rule | No weighting by role, no expiry of votes |
| D-023 | **Rollback (kill switch) skips four-eyes but requires a reason** | Incidents must not wait for a second approver; still fully audited | A malicious engineer could disable a feature alone. Acceptable: rollback reduces exposure, it never adds it |
| D-024 | **Transitions can `set` fields** (e.g. `rollout_pct: 10/100/0`), with from/to recorded in the audit event | Rollout % can't drift from state; no free-form edit form to secure | Arbitrary % (e.g. 25%) needs another transition, by design |
| D-025 | **Manifest `default` values with `@today+N` tokens** (refund `requested_at`, `sla_due`) | SLA filters work for records created in the UI, not only seed data | Tokens resolved at creation time, server clock (UTC) |
| D-026 | **Payout execution is a separate Ops Lead step after approval** | Separates "decide" from "move money" | No real PSP call; `execute_payout` only changes state |
